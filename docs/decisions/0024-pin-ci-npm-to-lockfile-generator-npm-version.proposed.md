# Pin CI npm to the lockfile-generator npm version

> Captured via /wr-architect:capture-adr (foreground-lightweight aside-invocation per ADR-032, derived-substance amendment 2026-07-06 / RFC-045). Section content was derived by the capturing agent from the in-session decision context; human-oversight: unconfirmed until ratified at the /wr-architect:review-decisions drain.

## Context and Problem Statement

The `build-and-test`, `publish`, and `auto-update` CI jobs pinned `npm@10.9.2` via an `npm install -g npm@X` step, but `package-lock.json` is regenerated locally by whatever npm the developer or agent session runs — currently npm 11.x. Across the npm 10→11 major boundary the lockfile shape changed, so `npm ci --prefer-frozen-lockfile` under the pinned npm 10 rejected the npm-11 lockfile (`Missing: conventional-commits-parser@7.1.0 from lock file`) and failed at the "Install dependencies" step. Every ci-publish run failed there, and because the release job only runs after build-and-test passes, the release pipeline stalled silently: the `feat(deprecation)` P029 minor bump (commit `7e77036`) sat unreleased on `main` across 3 consecutive failed runs, with no loud signal that the pipeline was wedged.

The `publish` job compounded the exposure — it ran `npm ci` with **no npm pin at all**, using node 22's bundled default npm (~10.x). So even a corrected `build-and-test` pin would not have covered the release step. Driver problem: P033. This ADR records the Option-B remediation the maintainer chose this session.

## Decision Drivers

- The release pipeline must not stall silently: a lockfile/npm mismatch surfaced only as an opaque `npm ci` failure at CI time, after the commit had already landed on `main`.
- Local development and CI must resolve the same lockfile — reproducibility across the dev→CI boundary is the whole point of `npm ci --prefer-frozen-lockfile`.
- The lockfile generator is not something the pipeline controls session-to-session (dev/agent sessions run current npm); the CI pin is the controllable knob, so it must track the generator, not the other way around.
- Every release-path job — not just the visible-failure one — must resolve the lockfile identically, or the drift merely moves downstream.

## Considered Options

1. **Align every release-path CI npm pin to the lockfile-generator npm (chosen)** — bump all three jobs to the npm version generating the committed lockfile (11.13.0) and give the publish job its own explicit pin.
2. **Pin CI to npm 10 and regenerate the lockfile under npm 10** — hold CI at the old pin and downgrade the lockfile to match.
3. **A `packageManager` / single-source-of-truth npm pin the workflows read** — remove the drift class entirely by deriving both the CI pin and the local npm from one declared version.

## Decision Outcome

Chosen option: **"Align every release-path CI npm pin to the lockfile-generator npm"**, because the lockfile is generated by the npm the dev/agent sessions actually run (npm 11.x) and the CI pin is the side that can be moved to match without fighting the local toolchain. The npm version pinned in every release-path CI job MUST equal the npm major/version that generates the committed `package-lock.json`. All three jobs (`build-and-test`, `publish`, `auto-update`) pin the same explicit npm version via an "Install specific npm version" step (currently 11.13.0), and no release-path job may rely on node's bundled default npm for `npm ci`. When a future session regenerates the lockfile under a newer npm major, the CI pins must be bumped in lockstep.

Option 2 was rejected because the dev/agent sessions run npm 11 and the lockfile would immediately re-drift on the next local install — it fights the toolchain instead of aligning to it. Option 3 (the durable fix that removes the drift class) is deferred to P033's investigation; this ADR records the immediate manual-alignment invariant, and P033 owns the single-source-of-truth mechanism that would make the invariant self-enforcing.

## Consequences

### Good

- The release pipeline resolves the committed lockfile identically in every job; the P029 fix published as `dry-aged-deps@2.17.0` on the first run after alignment.
- The publish job no longer depends on node's bundled default npm — its `npm ci` uses the same pinned npm the build job validated.

### Neutral

- The pin (11.13.0) is a fixed value that must be updated deliberately; it is now consistent across all three jobs, so the update is a single lockstep bump rather than a per-job hunt.

### Bad

- The invariant is enforced by convention, not by a check — a future lockfile regen under a newer npm major re-introduces the drift until someone bumps the pins. This residual risk is exactly what P033 tracks (a `check:lockfile`/prepush guard that fails fast on pin/lockfile mismatch, or Option 3's single source of truth).

## Confirmation

Under npm 11.13.0, both `npm ci --prefer-frozen-lockfile` and `npm run check:lockfile` pass with no diff in all three release-path jobs. Verified by ci-publish run `30179611319` (CodeQL → Build & Test → Release all green; `dry-aged-deps@2.17.0` published to npm). A future reader can re-verify by grepping `.github/workflows/*.yml` for `npm install -g npm@` and confirming every release-path job's pin matches the npm major that generated `package-lock.json` (`lockfileVersion` in the file).

## Pros and Cons of the Options

### Align every release-path CI npm pin to the lockfile-generator npm

- Good, because it makes CI resolve the exact lockfile local development produces, restoring `npm ci` reproducibility.
- Good, because it closes the unpinned-publish-job gap in the same change.
- Bad, because it is a manual invariant with no automated guard — it can silently re-drift.

### Pin CI to npm 10 and regenerate the lockfile under npm 10

- Good, because it requires no CI change (the pin already said npm 10).
- Bad, because the next local `npm install` under npm 11 rewrites the lockfile back to npm-11 shape, re-breaking CI — it does not hold.

### A `packageManager` / single-source-of-truth npm pin

- Good, because it removes the drift class entirely — one declared version drives both local and CI npm.
- Bad, because it is more than the immediate outage needed and warrants its own investigation (peer-dep/engine interactions, adopter portability) — deferred to P033 rather than rushed in under a release-blocking incident.

## Reassessment Criteria

Reopen this decision when: (a) P033 ships the single-source-of-truth mechanism or the fail-fast drift guard, at which point the manual-lockstep invariant here is superseded by the automated one; or (b) the project moves off `npm ci`-based CI (e.g. to a different package manager or a vendored-dependencies model), making the npm-pin/lockfile-generator coupling moot.
